> **Это перевод для чтения.** DSH загружает скилл из английского `SKILL.md` в этом же каталоге;
> файл `SKILL.ru.md` ничего не регистрирует.

# База знаний

Локальный markdown-корпус, собранный из HTML-экспортов Confluence. Одна статья на страницу
Confluence, с провенансом и метаданными свежести в шапке.

- Корень: по каталогу на источник, `~/.dsh/kb/<id>` (Windows: `C:\Users\<user>\.dsh\kb\<id>`). `--kb` выбирает один; без него движок берёт `KB_HOME`, иначе источник по умолчанию из реестра, иначе объясняет, что база не настроена.
- `INDEX.md` — сгенерированное оглавление по пространствам.
- `scripts/kb.py` — `import`, `inspect`, `fetch`, `search`, `get`, `audit`, `stats`, `index`, `pack`, `unpack`; `--version` печатает версию движка. Запускайте через `scripts/kb.ps1` в Windows или `scripts/kb` на остальных системах: оба находят рабочий Python.
- `MANIFEST.jsonl` — строка на страницу: хеш, даты, сигналы. Сравнение версий живёт здесь, а не в статье.

Пути `scripts/…` разрешаются относительно каталога этого скилла.

## Из какой базы берётся ответ

Источников может быть несколько, у каждого своя база (`~/.dsh/kb/<id>`). Инструменты определяют рабочую область вызывающего: область с
привязанным набором ищет ровно по этим источникам, иначе — по источнику по умолчанию. Каждое
попадание говорит, из какого оно источника; `kb_status` перечисляет источники, умолчание и то,
до каких дотянулся вызывающий. CLI ниже работает с одной базой за раз через `--kb`, поэтому
указывайте каталог нужного источника.

## Как отвечать по базе

Когда плагин `dsh-knowledge-base` установлен, основной путь — его инструменты: `kb_search`,
`kb_read`, `kb_review`, `kb_status`. Они возвращают провенанс с каждым попаданием, поэтому
отдельное правило, чтобы увидеть устаревание, не нужно. CLI ниже — на случай, когда плагина нет,
или для обслуживания.

1. **Ищите до ответа**; никогда не вспоминайте внутренний факт по памяти, если база может его
   хранить: `pwsh -File <skill>/scripts/kb.ps1 search "patroni etcd"`.
   FTS5 с префиксным совпадением: 2–4 характерных слова, по-русски или по-английски, кавычки не
   нужны.
2. **Читайте шапку каждого попадания** до того, как доверять телу. Решают четыре поля:
   - `status` — `current` пригоден; `legacy`/`deprecated` — это история, так и скажите.
   - `source_updated` — когда изменилась сама страница (`unknown` значит, что неизвестно).
   - `ingested` — когда был снят этот экспорт.
   - `review_after` — дата, после которой статью пора перепроверить.
3. **Читайте 1–3 статьи целиком**, а не фрагменты, если ответ процедурный. Используйте `get <id>`.
4. **Цитируйте использованное** в ответе: заголовок статьи или `id` + `source_updated`. Ссылку на
   статью давайте по **абсолютному** пути из строки `file=` (например,
   `[07. Статистика](C:/Users/me/.dsh/kb/confluence-fuzzy/projects/07-...md)`). Относительный путь
   разрешается от рабочего каталога сессии, а база лежит вне его, поэтому приложение ответит
   «файл не найден»; абсолютный путь открывает статью в боковой панели.
   Ещё инструмент печатает `source=` — адрес первоисточника в Confluence. Давайте и эту ссылку,
   чтобы читатель мог открыть страницу вики в браузере (куда именно — решает настройка DSH
   «Настройки → Общие → Открыть ссылки на чат в»: боковая панель в приложении или браузер по
   умолчанию).

## Правила свежести (обязательные)

Разделите то, что собираетесь сказать, на долговечное и изменчивое:

- **Долговечное**: почему было принято решение, обоснование архитектуры, компромиссы, режимы
  отказа, концептуальные объяснения. Возраст значит мало: старое обоснование остаётся верным
  рассуждением.
- **Изменчивое**: точные версии, IP-адреса, имена хостов, порты, пути, учётные данные, квоты,
  лимиты, шаги в интерфейсе, флаги команд. Оно тихо устаревает и при этом выглядит
  авторитетно.

Правила:

- Изменчивый факт из статьи, у которой `source_updated` старше ~6 месяцев или `unknown`, либо
  `status` не `current`, — **не** подавайте в настоящем времени. Либо проверьте вживую
  (командой, файлом конфигурации, `--version`), либо формулируйте как «по состоянию на <дата>, в
  статье <id> указано …» и пометьте как возможно устаревшее.
- Предпочитайте живую проверку вики, когда она дешёвая. Вики фиксирует замысел в момент времени;
  машина фиксирует настоящее.
- Если две статьи противоречат друг другу, предпочитайте более свежий `source_updated` и
  упомяните конфликт, а не выбирайте молча.
- Статьи со статусом `deprecated` остаются в базе намеренно (tombstone-записи). Используйте их,
  чтобы объяснять историю и предупреждать об удалённом, но никогда как текущую процедуру.

## Переопределения проекта

Перед ответом в проекте проверьте `<project>/.dsh/kb-overlay.md`. Он закрепляет факты,
специфичные для проекта («здесь PostgreSQL 18, а не 16», «другие адреса»), и **важнее базы**.
Когда оверлей противоречит статье, скажите, какому источнику вы следовали.

## Обслуживание базы

Импорт нового экспорта (идемпотентен, безопасен для повторного запуска):

```
pwsh -File <skill>/scripts/kb.ps1 import --zip <path> --base-url https://confluence.example
```

Либо загрузка прямо из REST API Confluence (Server/Data Center), все видимые пространства:

```
pwsh -File <skill>/scripts/kb.ps1 fetch --url https://confluence.example \
    --token $env:CONFLUENCE_TOKEN --space-type all
```

Confluence **Server**, который не поддерживает personal access token, игнорирует
`Authorization: Bearer` и отвечает как анонимный пользователь с пустым списком пространств. Там
используйте Basic-аутентификацию: имя пользователя — флаг, пароль — из окружения:

```
$env:CONFLUENCE_PASSWORD = '...'
pwsh -File <skill>/scripts/kb.ps1 fetch --url http://confluence.example:8090 \
    --user your.name --space-type all
```

`fetch` пишет архив в формате экспорта и прогоняет по нему тот же импортёр, поэтому внутри одной
базы загрузка через API и импорт файла сравниваются друг с другом. Разные *источники* держат
разные базы (см. «Из какой базы берётся ответ»), поэтому они никогда не сравниваются между
собой. Полезные флаги: `--spaces KEY1,KEY2`, `--since 2026-11-01` (только страницы, изменённые
после даты), `--list-spaces`, `--no-attachments`, `--save-zip <file>`, чтобы сохранить
загруженное.

Перед импортом архив можно проверить, не трогая базу:

```
pwsh -File <skill>/scripts/kb.ps1 inspect --zip <path> [--json]
```

Он сообщает размер, число HTML-файлов страниц и пространства, найденные в каждом `index.html`,
со стабильными кодами ошибок (`file-missing`, `file-empty`, `file-not-zip`, `file-no-pages`).
`import --spaces KEY` сужает мультипространственный архив; страницы остальных пространств
по-прежнему считаются присутствующими, поэтому сужение никогда не превращает их в tombstone.

И `import`, и `fetch` принимают `--progress`, который печатает в stderr строки
`PROGRESS <done>/<total> <space>`, по одной на страницу (пространство может отсутствовать, пока
оно неизвестно). Страница настроек DSH разбирает ровно этот формат; держите его стабильным.

- Неизменённые страницы остаются побайтово прежними, поэтому добавленные руками заметки выживают.
- Изменённые страницы перегенерируются из экспорта; поля шапки `status`, `tags`, `notes`,
  `owner`, `review_after`, `pin` сохраняются.
- Страницы, исчезнувшие из нового экспорта, становятся tombstone (`status: deprecated`,
  `deprecated_on`), но никогда не удаляются.
- После этого запустите `audit`, чтобы увидеть очередь ревизии, и `stats` для счётчиков.

Когда плагин установлен, «Настройки → База знаний» управляют тем же движком: там хранятся
источник (URL сервера + токен либо путь к экспорту), выбранные пространства и расписание,
показывается прогресс с кнопкой «Остановить», а каждый запуск записывается на страницу задач
автоматизации.

### Перенос базы на другую машину

```pwsh
pwsh -File <skill>/scripts/kb.ps1 pack --out base.zip --meta meta.json
pwsh -File <skill>/scripts/kb.ps1 unpack --archive base.zip --check --json
pwsh -File <skill>/scripts/kb.ps1 --kb <dest> unpack --archive base.zip --json
```

В архиве статьи, `MANIFEST.jsonl`, `kb.sqlite`, вложения и `knowledge-base.json` с именем
источника, его видом, базовым URL, пространствами и расписанием. Учётных данных в нём нет.
Архивы со старым маркером `confluence-kb.json` / `dsh-confluence-kb-base` ещё открываются;
`pack --progress` печатает `PACK <done>/<total>`.
`unpack --check` проверяет архив, ничего не записывая; восстановленная база продолжает
обновляться с того же сервера с теми кредами, что есть на новой машине. На странице настроек
это «Экспортировать базу» и «Импортировать базу»; у импортированной базы URL фиксируется —
другой сервер это новый источник, а не правка старого.

Ревизия статьи после проверки:

- Правки тела теряются при следующем импорте — записывайте выводы в шапку:
  `review_after: 2027-01-01`, `notes: "проверено на pg01 2026-11-20, версия 17.2"`.
- Помечайте замещённое содержимое `status: legacy` и указывайте `superseded_by: <id>` вместо
  удаления.

## Ограничения

- Вложения (схемы, PDF, ini-файлы) лежат в `attachments/<pageId>/` как файлы, а не как
  индексированный текст; открывайте их по пути, когда статья на них ссылается.
- Макросы без экспортированного представления (Jira, исходник drawio, include) выглядят как
  заглушки вроде `*[Jira macro not exported]*`. Говорите, что данных нет, а не выдумывайте.
- Поисковый индекс производный; `kb.py index` пересобирает его, если `kb.sqlite` отсутствует или
  устарел.
- Один `id` — один файл. Импорт удаляет устаревшего двойника с тем же `id` (в сводке это
  `duplicates`), а индекс держит одну строку на `id` и предупреждает об остатках вместо падения.
- Заголовки вложений приводятся к переносимому виду: `image 21:0:24.png` становится
  `image 21_0_24.png` и на диске, и в ссылке статьи.
- Страницы с пустым телом пропускаются («no content») и в базу не попадают.
